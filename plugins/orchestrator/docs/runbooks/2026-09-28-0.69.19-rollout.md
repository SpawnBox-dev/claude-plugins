## 3. Reload lanes, one at a time (Jarid types; agents verify)

**Order:** idle lanes first, then lanes waiting for the slot, then the slot holder at a handover, then PA last.

Tradeoff to know: the new `unrouted_transcript` alarm runs only in **PA's** watcher. Until PA reloads, a lane on the old plugin that runs `/clear` breaks silently, as it did on 09-27. So **nobody runs `/clear` until PA is on 0.69.19.**

Per lane:

1. **[JARID]** `/reload-plugins` in that lane's terminal, at a turn boundary.
   - It must print `Reloaded: N plugins · ... · N hooks · N plugin MCP servers ...`.

   - Docs (code.claude.com/docs/en/plugins/cli-reference, `/reload-plugins`): "Apply pending plugin changes to the running session without restarting it", and it reloads hooks and plugin MCP servers. So no window restart is needed.

## Mixed-version safety (why reloading one lane at a time is fine)

- **Schema:** a 0.69.19 process adds the nullable `sessions.transcript_id` column. 0.69.18 code selects and inserts named columns only, so it neither reads nor clears it.
- **Routing:** a 0.69.18 watcher ignores `transcript_id`. A reloaded lane that has NOT run `/clear` writes `<session_id>.jsonl` as before, so old watchers still route it. Only a `/clear` needs the new code on the RECEIVER too. That is the other reason for "nobody runs `/clear` until PA is on 0.69.19".
- **Alerts:** a 0.69.18 lane still broadcasts the old `client_transport_suspect` text. Per KB 27f1613d, it is relayed to Jarid, not dismissed.
